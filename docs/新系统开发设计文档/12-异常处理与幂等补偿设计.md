# 12-异常处理与幂等补偿设计

## 1. 文档目标与适用范围

| 项目 | 说明 |
|---|---|
| 文档定位 | 本文是对 `00` 至 `11` 号新系统开发设计文档的补充说明，专门细化异常处理、幂等控制、补偿入口和人工处理口径。 |
| 适用范围 | 适用于下单支付、退款、发货物流、电子发票与红冲、采购供货商协同、收款对账、通知审批和跨模块异常补偿。 |
| 不改变内容 | 不改变已定义的模块边界、领域模型、数据库表、状态枚举和 API 接口；不新增旧系统字段、旧接口或旧架构依赖。 |
| 设计依据 | 以新系统开发设计文档和原型设计方案中的状态机、模块边界、数据字典、数据库设计、接口文档、外部联调说明和权限矩阵为依据。 |
| 核心目标 | 保证外部平台成功、失败、超时、重复回调、乱序回调和内部副作用失败均可追踪、可重试、可人工补偿。 |
| 读者对象 | 后端开发、前端开发、测试、联调人员、客服、仓管、代账、管理员和项目验收人员。 |

本文遵循以下边界：

| 边界 | 处理口径 |
|---|---|
| 不继承旧系统 | 不引用历史失败项目的代码、数据库、接口、配置或状态口径作为依据。 |
| 不跨系统原子回滚 | 外部支付、退款、运单、发票等结果已经产生时，系统不承诺跨系统一致回滚，进入异常待处理和人工补偿。 |
| 不绕过状态机 | 人工补偿只能在业务模块允许的状态机范围内完成，不允许通过后台直接改库跳过支付、退款、发货、开票、采购等业务规则。 |
| 主链路与弱依赖分离 | 支付成功、退款成功、开票成功等主状态不因通知、企微卡片、邮件、线索回写等弱依赖失败而回滚。 |
| 回调统一落库 | 支付、退款、物流、开票、红冲、企微审批和企微卡片回执先写入 `integration_callback_event`，再由业务模块幂等处理。 |
| 日志不可变更 | 退款、发货、采购、开票、红冲、对账、补偿处理和导出等敏感操作必须写 `audit_operation_log`，日志不可编辑、不可删除。 |

## 2. 幂等设计总原则

### 2.1 幂等键分层

| 幂等来源 | 适用场景 | 推荐键或唯一键 | 处理原则 | 冲突处理 |
|---|---|---|---|---|
| 客户端幂等键 | 创建订单、退款申请、发货、开票、采购确认、材料上传等写操作 | `Idempotency-Key` + 业务对象 ID 或客户端请求号 | 同一请求重复提交时返回同一业务结果，不重复创建单据。 | 相同键但请求关键字段不同，返回幂等冲突并记录日志。 |
| 业务唯一键 | 订单、支付记录、发货单、退款单、发票单、采购单、通知等内部单据 | `order_no`、`merchant_order_no`、`refund_no`、`shipment_no`、`invoice_apply_no`、`purchase_no` 等 | 单据创建以业务编号和领域唯一约束兜底，避免并发重复。 | 已存在则返回既有单据或 `409` 状态冲突。 |
| 外部流水号 | 支付、退款、物流、发票、红冲等外部结果 | `external_payment_no`、`external_refund_no`、`tracking_no`、`invoice_no`、`red_invoice_no` | 外部平台已产生唯一结果时，内部只能绑定一次。 | 同一外部流水关联不同业务单据时进入人工核对。 |
| 回调事件 ID | 外部异步回调 | `source_system + event_no` | 所有外部回调先写入 `integration_callback_event`，重复事件直接按已处理结果返回。 | 重复事件内容不一致时记录异常，不重复执行业务副作用。 |
| 回调业务幂等键 | 支付、退款、物流、开票、红冲、企微审批 | `merchant_order_no + external_payment_no`、`refund_no + external_refund_no`、`tracking_no + logistics_node_time + node_status`、`invoice_apply_no + invoice_no`、`invoice_apply_no + red_invoice_no`、`wecom_approval_id` | 业务模块按领域键幂等，避免重复开通权益、重复扣库存、重复通知、重复开票或重复入库。 | 已达终态时忽略低优先级或乱序回调，保留原始摘要。 |
| 文件摘要 | 对账导入、发票文件、红冲凭证、退款凭证、代账材料 | `bill_month + bill_source + file_digest`、`file_digest + biz_type + biz_id` | 同一文件不重复导入或重复绑定同一业务对象。 | 重复文件返回既有批次或文件引用。 |
| 通知幂等键 | 站内通知、微信订阅消息、企微卡片 | `idempotency_key + channel + receiver_user_id` | 同一业务事件同一通道同一接收人只生成一条通知。 | 失败重试更新同一通知记录的 `retry_count` 和 `failure_reason`。 |

### 2.2 重复提交处理

| 场景 | 识别方式 | 系统处理 | 返回口径 | 日志要求 |
|---|---|---|---|---|
| 同一客户端请求重复提交 | `Idempotency-Key` 与业务键一致 | 返回首次成功创建或受理的业务对象，不重复创建。 | 成功返回既有 `order_id`、`refund_id`、`shipment_id` 等。 | 记录幂等命中次数、请求摘要和 `trace_id`。 |
| 同一业务对象存在进行中单据 | 业务唯一约束或状态校验命中 | 按状态机拒绝重复操作，例如同一订单已有审核中退款。 | 返回 `409` 或业务状态冲突提示。 | 记录操作人、目标对象、当前状态和冲突原因。 |
| 相同幂等键但关键参数变化 | 幂等键一致，金额、订单、收货地址、退款金额等关键字段不一致 | 不复用既有结果，阻断并要求重新生成请求键。 | 返回 `DUPLICATE_REQUEST` 或 `STATE_CONFLICT`。 | 记录前后参数摘要，不记录敏感明文。 |
| 页面重复点击 | 前端按钮重复触发，后端收到多次写请求 | 后端仍以幂等键和状态机为准，不依赖前端防抖保证正确性。 | 首次成功，后续返回既有结果或状态冲突。 | 记录可选，敏感写操作必须有审计日志。 |

### 2.3 重复回调与乱序回调处理

| 场景 | 识别方式 | 系统处理 | 回调响应 | 日志要求 |
|---|---|---|---|---|
| 同一回调事件重复到达 | `source_system + event_no` 已存在 | 不重复执行业务处理，返回既有 `processing_status`。 | 通常返回成功或已受理，避免外部平台无限重试。 | `integration_callback_event` 记录重复命中。 |
| 同一业务结果重复到达 | 业务幂等键已存在 | 不重复生成支付记录、权益、库存流水、发票、通知或审批回写。 | 返回当前业务对象状态。 | 记录幂等键、目标对象和处理结果。 |
| 成功回调后又收到失败回调 | 终态已成功，例如 `PAID`、`REFUNDED`、`ISSUED`、`RED_REVERSED` | 终态不回退，失败回调标记已忽略或异常摘要。 | 返回已处理。 | 记录乱序原因、原终态和回调摘要。 |
| 失败回调后又收到成功回调 | 业务尚未终态成功 | 校验金额、业务单号和状态后，可按成功回调推进状态。 | 返回处理结果。 | 记录状态变化前后快照。 |
| 回调对象不存在 | 单号、流水号或关联对象无法匹配 | 写入回调事件，业务处理失败，进入异常待处理或人工核对。 | 返回已受理或业务校验失败，按平台重试策略确定。 | 记录原始摘要、失败原因和重试次数。 |
| 回调验签失败 | 签名、时间戳或随机串校验失败 | 拒绝业务处理，不写入核心业务单据；可保留安全审计摘要。 | 返回鉴权失败。 | 记录来源、时间、摘要，不记录密钥和完整敏感原文。 |

### 2.4 关键场景幂等键汇总

| 业务场景 | 幂等键 | 成功结果 | 异常补偿 |
|---|---|---|---|
| 创建订单 | `Idempotency-Key + student_id + spec_id + client_request_no` | 返回同一 `order_id` 和 `merchant_order_no` | 响应失败后按幂等键查询返回。 |
| 支付回调 | `source_system + event_no`、`merchant_order_no + external_payment_no` | 订单 `payment_status=PAID`，写支付记录并触发后置动作 | 金额不一致、已关闭后成功、支付记录缺失进入异常待处理。 |
| 退款申请 | `order_id + student_id + Idempotency-Key` | 创建 `pay_refund`，订单 `refund_status=REVIEWING` | 存在进行中退款时拒绝重复申请。 |
| 退款回调 | `source_system + event_no`、`refund_no + external_refund_no` | 退款单 `status=REFUNDED`，执行退款成功副作用 | 已退款终态不被失败覆盖，副作用失败进入补偿。 |
| 发货确认 | `shipment_no` 或 `tracking_no` | 发货单 `status=SHIPPED`，库存流水出库 | 外部已出单但内部失败时标记发货异常。 |
| 物流轨迹 | `tracking_no + logistics_node_time + node_status` | 写入轨迹，签收时同步 `SIGNED` | 乱序轨迹保留但不回退主状态。 |
| 开票回调 | `source_system + event_no`、`invoice_apply_no + invoice_no` | 发票 `status=ISSUED` | 自动失败转 `TO_BE_ISSUED`，文件缺失进入补偿。 |
| 红冲回调 | `source_system + event_no`、`invoice_apply_no + red_invoice_no` | 发票 `status=RED_REVERSED` | 红冲失败保留 `ISSUED` 并支持重试或人工上传凭证。 |
| 采购入库 | `purchase_no + inbound_batch_no` | 采购完成，生成入库库存流水 | 数量不一致进入人工确认，不自动完成。 |
| 对账导入 | `bill_month + bill_source + file_digest` | 生成对账批次和明细 | 重复上传返回已有批次，导入失败记录原因。 |
| 通知发送 | `idempotency_key + channel + receiver_user_id` | 生成一条通知或发送记录 | 外部通知失败不回滚主业务。 |

## 3. 支付异常与补偿

| 异常场景 | 触发条件 | 识别方式 | 系统处理 | 是否自动重试 | 是否进入人工补偿 | 最终状态 | 日志要求 |
|---|---|---|---|---|---|---|---|
| 支付创建失败 | 小程序订单已创建，调用支付适配器获取支付参数失败，且外部未明确受理支付 | 支付适配器返回失败、无 `external_payment_no`、订单仍为 `PENDING` | 订单保持 `payment_status=PENDING`，提示可稍后继续支付；未超过支付截止时间允许重新拉起支付。 | 否，除非失败原因属于平台短暂不可用，可由用户再次发起。 | 否，持续失败可由客服查看订单和支付失败日志。 | 未超时为 `PENDING`；到期未支付后为 `CLOSED`。 | 记录 `trace_id`、`merchant_order_no`、失败原因、适配器摘要，不记录真实密钥。 |
| 支付创建结果未知 | 支付适配器超时或网络中断，无法确认外部是否已受理 | 调用超时、无明确失败码、回调事件未到达 | 订单保持 `PENDING`，禁止立即重复创建不同商户订单号；通过查询补偿确认外部结果。 | 是，按商户订单号查询有限次数。 | 查询仍无法确认时进入支付异常核对。 | 确认未支付则保持 `PENDING` 或超时关闭；确认已支付则按支付成功处理。 | 记录查询次数、最后一次查询结果和处理人。 |
| 用户取消支付 | 用户在微信支付或 Mock 支付页主动取消 | 小程序返回取消、未收到成功回调、支付截止时间未到 | 支付状态保持 `PENDING`，允许继续支付；不创建退款单。 | 否。 | 否。 | 未超时为 `PENDING`；到期后为 `CLOSED`。 | 记录取消摘要和客户端 `trace_id`，不作为失败告警。 |
| 支付超时 | 超过 `payment_expire_at` 且未收到成功支付回调 | 定时任务或查询补偿确认无成功支付 | 关闭继续支付入口，订单 `payment_status=CLOSED`。 | 是，关闭前可做一次或多次查询确认。 | 一般否；查询结果不一致时进入人工核对。 | `CLOSED`。 | 记录关闭时间、关闭原因、查询摘要。 |
| 支付成功回调重复 | 外部平台重复推送同一成功事件 | `source_system + event_no` 或 `merchant_order_no + external_payment_no` 已处理 | 返回已处理结果，不重复生成支付记录、学习权益、发货任务和通知。 | 否。 | 否。 | 订单保持 `PAID`，回调事件为已处理或已忽略。 | 记录幂等命中、原处理事件号和重复回调摘要。 |
| 支付回调乱序 | 已处理成功后又收到失败或关闭回调，或先收到失败后再收到成功 | 订单支付状态与回调结果不匹配，且回调事件时间晚于或早于已处理结果 | 成功终态不被失败覆盖；若订单仍 `PENDING` 且成功回调通过验签和金额校验，可推进为 `PAID`。 | 否。 | 异常组合进入人工核对。 | 合法成功为 `PAID`；非法或低优先级回调不改变主状态。 | 记录回调时间、平台事件号、处理决策和前后状态。 |
| 系统已关闭但外部已支付 | 订单已 `CLOSED` 后收到平台成功回调，或账单显示已支付 | `payment_status=CLOSED` 且回调或账单存在成功支付流水 | 不自动开放权益；先记录支付异常，核对金额、商户订单号和外部流水。确认真实支付后补写支付记录并执行支付成功后置动作；无法确认时保持关闭并人工说明。 | 可自动查询平台流水。 | 是，财务或代账核对，客服可协助处理学员沟通。 | 确认支付成功后转 `PAID`；未确认保持 `CLOSED` 并记录处理结论。 | 记录外部流水、核对人、核对结论、权益是否补开、发货任务是否补建。 |
| 支付记录缺失 | 订单已 `PAID`，但 `pay_payment` 未写入或写入失败 | 订单支付状态与支付记录数量不一致；支付成功回调事件已存在 | 主订单不回滚；根据回调事件和商户订单号补写 `pay_payment`，再检查权益、发货和通知副作用。 | 是，可由补偿任务自动补写。 | 自动补写失败时进入人工补偿。 | 订单保持 `PAID`，支付记录补齐。 | 记录缺失检测来源、补写字段摘要、补写结果和操作人。 |
| 支付金额不一致 | 回调支付金额与订单应付金额不一致 | `paid_amount_cent != payable_amount_cent` | 不更新为 `PAID`，写回调异常，进入人工核对。 | 否。 | 是。 | 核对前保持原支付状态；确认异常后按人工结论处理。 | 记录订单金额、回调金额、外部流水、核对备注。 |

## 4. 退款异常与补偿

| 异常场景 | 触发条件 | 识别方式 | 系统处理 | 是否自动重试 | 是否进入人工补偿 | 最终状态 | 日志要求 |
|---|---|---|---|---|---|---|---|
| 审核通过后原路退款失败 | 客服审核通过并调用原路退款，平台返回失败或失败回调 | `pay_refund.status=PROCESSING` 且退款结果失败 | 退款单转 `FAILED`，保存失败原因；客服可重试退款或转 `MANUAL_REQUIRED`。 | 可按失败类型配置有限重试。 | 是，失败后可转人工退款。 | `FAILED`、重试后 `PROCESSING`，或转 `MANUAL_REQUIRED`；最终成功为 `REFUNDED`。 | 记录审核人、退款金额、外部失败码、重试次数和处理结论。 |
| 原路退款接口超时 | 调用退款适配器后无明确受理或失败结果 | 接口超时、无 `external_refund_no` 或回调未到 | 退款单保持 `PROCESSING`，通过查询补偿确认是否已受理或已退款。 | 是，按退款单号或商户订单号查询。 | 查询仍不明确时进入人工核对。 | 确认成功为 `REFUNDED`；确认失败为 `FAILED`；未知保持 `PROCESSING` 并待处理。 | 记录每次查询结果、平台响应摘要和最后处理人。 |
| 退款回调重复 | 平台重复推送同一退款结果 | `source_system + event_no` 或 `refund_no + external_refund_no` 已处理 | 返回当前退款状态，不重复冻结权益、生成红冲待办、通知或对账影响。 | 否。 | 否。 | 保持当前退款状态，通常为 `REFUNDED`。 | 记录幂等命中和重复事件摘要。 |
| 退款状态乱序 | 已退款后收到失败回调，或失败后又收到成功回调 | 回调结果与当前 `pay_refund.status` 不匹配 | `REFUNDED` 终态不被失败覆盖；非终态下成功回调经金额校验后可推进到 `REFUNDED`。 | 否。 | 状态冲突无法判断时进入人工核对。 | 成功确认后 `REFUNDED`；低优先级乱序回调不改变终态。 | 记录当前状态、回调状态、外部退款流水、处理决策。 |
| 待人工退款 | 审核通过但未接入原路退款、原路退款不可用或客服转人工 | 退款单状态为 `MANUAL_REQUIRED` | 生成财务或代账待办；未登记凭证前不允许置为已退款。 | 否。 | 是。 | 凭证登记完成后 `REFUNDED`。 | 记录转人工原因、责任人、处理时限和后续凭证。 |
| 人工退款凭证补录 | 代账或财务已线下退款，需要补录凭证 | `MANUAL_REQUIRED` 状态下提交退款渠道、退款时间、凭证号和凭证文件 | 校验凭证完整性，成功后退款单转 `REFUNDED` 并触发退款成功副作用。 | 否。 | 是。 | `REFUNDED`。 | 记录操作人、退款渠道、凭证号、文件引用、前后状态。 |

| 重复记录 | 同批次或系统中同一商户订单号、外部流水重复 | 对账规则判定 `DUPLICATE`，或唯一键冲突 | 保留所有候选记录，人工确认有效记录，不自动删除账单行。 | 否。 | 是。 | `result=DUPLICATE`，核对后标记已核对。 | 记录重复来源、候选记录和最终选择。 |

## 9. 通知与审批异常

| 异常场景 | 触发条件 | 识别方式 | 系统处理 | 是否自动重试 | 是否进入人工补偿 | 最终状态 | 日志要求 |
|---|---|---|---|---|---|---|---|
| 站内通知生成失败 | 支付成功、退款成功、开票完成、对账差异等业务事件需要站内通知，但通知记录创建失败 | 业务主状态已变更，`notify_message` 缺失或创建失败 | 主业务不回滚；自动重试生成站内通知；失败后进入异常待处理或待办兜底。 | 是。 | 自动失败后进入人工补偿。 | 通知最终 `SENT` 或保留失败原因；主业务保持已完成状态。 | 记录业务事件、接收人、失败原因、重试次数。 |
| 订阅消息未授权 | 学员未授权对应微信订阅模板，或授权已失效 | 授权状态缺失或发送前校验失败 | 不发送订阅消息，以站内通知兜底；不影响支付、退款、课程提醒等主流程。 | 否。 | 否。 | 不生成外部订阅发送，或记录为不可发送；站内通知正常。 | 记录授权状态摘要，不作为异常告警。 |
| 订阅消息发送失败 | 学员已授权但微信订阅消息发送失败 | 发送适配器返回失败或超时 | 不回滚业务；记录失败原因，可按策略重试；站内通知作为必达通道。 | 可重试。 | 一般否。 | 外部通知 `FAILED` 或重试后 `SENT`。 | 记录模板、接收学员、失败原因。 |
| 企微卡片发送失败 | 审批、待办、库存预警、对账差异等企微卡片发送失败 | `notify_message.channel=WECOM_CARD` 且 `send_status=FAILED` | 不回滚待办或主业务；PC 待办列表兜底；可重试发送。 | 是。 | 持续失败时管理员或对应负责人处理。 | 企微通知 `FAILED` 或重试后 `SENT`；业务状态不变。 | 记录接收人、企微用户绑定状态、失败原因。 |
| 接收人未绑定企微 | 需要发送企微卡片，但接收人无 `wecom_user_id` | 用户绑定字段为空或禁用 | 不发送企微卡片，保留 PC 待办；提示管理员补全企微绑定。 | 否。 | 是，管理员维护人员绑定。 | 通知保持失败或不可发送；待办仍可在 PC 查看。 | 记录接收人、场景码和绑定缺失原因。 |
| 审批结果重复回调 | 企业微信重复推送同一审批结果 | `source_system + event_no` 或 `wecom_approval_id` 已处理 | 返回已处理结果，不重复回写课程、采购、角色等业务状态。 | 否。 | 否。 | 审批保持 `APPROVED`、`REJECTED` 或 `CANCELED`。 | 记录幂等命中和审批实例 ID。 |
| 审批回调对象状态已变化 | 审批回调到达时，业务对象已取消、已处理或状态不再允许回写 | 审批状态与业务对象状态机不匹配 | 审批记录可保存回调结果，但业务回写失败，进入异常补偿，由业务模块负责人确认。 | 可重试一次状态校验。 | 是。 | 审批状态按平台结果记录；业务状态按人工确认处理。 | 记录审批结果、业务对象前后状态和处理结论。 |
| 拒绝原因缺失 | 审批拒绝或退款拒绝未填写必要原因 | 请求或回调缺少拒绝原因 | 阻断业务拒绝完成，或将回调标记处理失败并待人工补充。 | 否。 | 是。 | 状态不推进到拒绝，直到补齐原因。 | 记录缺失字段和处理人。 |

## 10. 数据一致性与人工补偿入口

### 10.1 异常待处理列表

异常待处理列表是通知审批模块和各业务模块的聚合工作台，不要求新增数据库表。列表数据从已有业务状态、异常标记、回调事件、失败原因和操作日志中聚合。

| 异常来源 | 聚合条件 | 主要处理角色 | 可执行动作 | 不允许动作 |
|---|---|---|---|---|
| 支付异常 | `integration_callback_event` 支付处理失败、金额不一致、已关闭后成功、支付记录缺失 | 客服、代账、超级管理员 | 查询补偿、补写支付记录、确认开放权益、标记已处理 | 未核对外部流水前直接开通权益。 |
| 退款异常 | `pay_refund.status=FAILED/MANUAL_REQUIRED`，或退款成功副作用失败 | 客服、代账、超级管理员 | 重试原路退款、转人工退款、上传凭证、补偿权益和红冲待办 | 凭证缺失时确认已退款。 |
| 发货物流异常 | `fulfillment_shipment.exception_flag=true`、运单缺失、面单或打印失败、签收同步失败 | 仓管、超级管理员 | 补录运单、重取面单、重试云打印、库存流水校正、人工签收 | 对未支付或已退款待发货订单继续发货。 |
| 发票红冲异常 | `tax_invoice.status=TO_BE_ISSUED`、红冲失败、发票文件缺失 | 代账、超级管理员 | 人工开票、上传发票文件、重试红冲、上传红字发票或凭证 | 用红冲替代退款。 |
| 采购协同异常 | 审批回写失败、供货商推送失败、进项票缺失、收货数量不一致 | 仓管、代账、超级管理员 | 重试审批回写、重发供货商通知、确认收货差异、催办进项票 | 审批未通过时推送供货商。 |
| 对账异常 | `AMOUNT_DIFF`、`FEE_DIFF`、`UNMATCHED`、`DUPLICATE`、导入失败 | 代账、超级管理员 | 重新导入、标记已核对、填写差异原因、导出差异 | 通过对账直接改变支付或退款状态。 |
| 通知审批异常 | 站内通知生成失败、企微卡片失败、审批回调失败 | 对应模块负责人、超级管理员 | 重试通知、PC 待办兜底、审批回调重放、人工关闭 | 通知失败后回滚主业务状态。 |

### 10.2 人工补偿动作

| 补偿动作 | 适用场景 | 前置校验 | 处理结果 | 日志要求 |
|---|---|---|---|---|
| 重试 | 外部调用超时、回调处理失败、通知发送失败、面单拉取失败、红冲失败 | 对象仍处于可重试状态，幂等键未冲突，重试次数未超过配置 | 更新同一业务记录或回调事件的 `retry_count`、`failure_reason` 和处理状态 | 记录重试人、重试时间、重试前后摘要。 |
| 转人工 | 原路退款失败、自动开票失败、红冲失败、外部协同长期失败 | 自动处理已失败或配置未接入，业务状态允许人工处理 | 生成或展示人工待办，业务状态按既有枚举进入 `MANUAL_REQUIRED`、`TO_BE_ISSUED` 或保持原状态待处理 | 记录转人工原因、责任角色和处理时限。 |
| 上传凭证 | 人工退款、人工开票、人工红冲、代账材料、发票文件补录 | 文件类型、大小、摘要、业务对象和操作权限校验通过 | 保存文件引用，业务状态推进到对应完成状态 | 记录文件编号、文件摘要、上传人，不记录敏感明文。 |
| 标记已处理 | 对账差异核对、异常回调已人工确认、通知失败已兜底处理 | 必须填写处理备注；涉及资金、发票、库存的异常需有凭证或核对结论 | 异常从待处理列表移出或标记已核对，主业务状态按状态机保持或推进 | 记录处理人、处理结论、备注和关联凭证。 |
| 人工关闭 | 确认无需继续处理、重复异常、外部事件无效 | 必须有关闭原因；不得关闭仍影响资金、权益、库存或发票一致性的异常 | 异常记录保留关闭原因，不删除原始记录 | 记录关闭人、关闭原因和审批或复核要求。 |
| 补写子单据 | 支付记录缺失、发货任务缺失、红冲待办缺失、通知记录缺失 | 主状态已确认，来源回调或业务事件可追溯，幂等键唯一 | 补齐缺失记录，并重新检查后续副作用 | 记录补写来源、补写字段摘要、前后状态。 |
| 库存校正 | 外部已发货但库存流水缺失、采购入库数量差异 | 仓管或管理员权限，必须关联发货单或采购单 | 通过库存流水补写或校正，不直接无日志改库存余额 | 记录 SKU、数量、方向、业务单号和校正原因。 |

### 10.3 数据一致性检查

| 检查项 | 检查规则 | 异常处理 |
|---|---|---|
| 订单与支付记录 | `payment_status=PAID` 的订单应存在成功支付记录，金额与订单应付一致。 | 支付记录缺失则补写；金额不一致进入人工核对。 |
| 订单与学习权益 | 支付成功订单应按课程、规格和学员存在学习权益；退款成功后权益应冻结或撤销。 | 权益缺失或未冻结时自动补偿，失败后进入教务/客服待处理。 |
| 订单与发货单 | 含实物订单支付成功后应有待发货任务；退款成功后待发货操作应关闭。 | 发货任务缺失由仓管补建；已退款仍发货则阻断并记录冲突。 |
| 发货与库存流水 | `SHIPPED` 发货单应存在对应出库库存流水，且幂等键唯一。 | 缺失则补写库存流水；冲突进入库存校正。 |
| 退款与发票红冲 | 已退款且发票 `ISSUED` 的订单应有红冲待办或红冲结果。 | 红冲待办缺失则补建，红冲失败可重试或人工上传凭证。 |
| 发票与文件 | `ISSUED` 发票应有发票号码和可追溯文件或文件处理说明。 | 文件缺失时自动拉取或人工上传。 |
| 采购与库存入库 | `COMPLETED` 采购单应有关联入库批次和库存流水。 | 入库缺失或数量不一致进入采购人工确认。 |
| 对账与支付退款 | 对账差异不得反向直接修改支付或退款状态。 | 差异只进入核对备注、补偿任务或查询补偿。 |
| 通知与待办 | 主业务成功但通知失败时，不回滚主业务；站内通知为系统内兜底通道。 | 自动重试通知或保留 PC 待办入口。 |

### 10.4 操作日志要求

| 日志类别 | 必填内容 | 脱敏要求 |
|---|---|---|
| 外部回调日志 | `trace_id`、`source_system`、`event_no`、`event_type`、幂等键、业务对象编号、处理状态、失败原因、重试次数 | 不保存真实密钥、完整签名原文和敏感个人信息明文。 |
| 人工补偿日志 | 操作人、角色、目标对象、补偿动作、前后状态、处理备注、凭证文件引用 | 手机号、税号、地址、凭证敏感内容按权限脱敏。 |
| 资金相关日志 | 订单号、商户订单号、支付或退款流水、系统金额、外部金额、核对结论 | 不记录完整银行卡、密钥或平台敏感配置。 |
| 发货库存日志 | 发货单、运单号、SKU、数量、库存前后摘要、库存流水幂等键 | 收货地址按最小必要原则脱敏展示。 |
| 发票税务日志 | 发票申请号、发票号、红字发票号、文件引用、税务快照摘要、失败原因 | 税号、邮箱和文件下载需鉴权，日志只存脱敏值或文件引用。 |
| 对账导入日志 | 账单月份、来源、文件摘要、导入人、导入结果、差异统计 | 不记录真实支付平台密钥或完整敏感账单原文。 |
| 通知审批日志 | 通知场景、通道、接收人、发送状态、审批实例、审批结果、回写结果 | 企微用户标识和通知内容按权限控制。 |
