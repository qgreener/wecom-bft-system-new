# 05-数据库设计文档

## 1. 文档定位

| 项目 | 说明 |
|---|---|
| 文档目标 | 基于 `04-领域模型与数据字典.md` 将核心领域对象落到数据库表、字段类型、主键、唯一键、索引、外键或逻辑关联、状态枚举、审计字段和软删除策略 |
| 上游依据 | `00-文档说明.md`、`02-业务流程与状态机说明.md`、`03-模块设计文档.md`、`04-领域模型与数据字典.md` |
| 设计边界 | 仅给出表结构建议，不写具体 SQL；不继承历史失败产物中的历史库表、字段、接口和配置 |
| 重点约束 | 订单是支付、学习权益、发货、退款、发票、对账、代账材料的主追溯入口；订单必须拆分支付、履约、退款、开票四类状态 |

## 2. 总体设计原则

| 原则 | 数据库落点 |
|---|---|
| 订单中心 | 支付、发货、退款、发票、对账、代账材料均建议保存 `order_id`，并冗余 `order_no` 便于导出、对账和人工排查 |
| 单据链可追溯 | 子单据保留自身业务编号，同时写入 `order_document_link` 作为订单详情页统一单据链索引 |
| 状态拆分 | `trade_order` 不设置单一 `order_status`，只保存 `payment_status`、`fulfillment_status`、`refund_status`、`invoice_status` |
| 子单据自治 | 支付记录、退款单、发货单、发票单、采购单、对账记录、代账材料各自保存状态和生命周期时间 |
| 快照不可变 | 订单、订单明细、发货单、发票单保存课程规格、价格、税务、收货地址、发票抬头等下单或申请时快照 |
| 幂等优先 | 支付、退款、物流、开票、红冲、采购入库、对账导入均设置业务幂等键或唯一键 |
| 审计不可绕过 | 交易单据不物理删除；退款、发货、采购、开票、红冲、配置、导入导出等关键动作写 `audit_operation_log` |
| 软删除谨慎 | 主数据可软删除或停用；交易、支付、退款、发货、发票、对账、代账材料、审计日志默认不软删除 |

## 3. 字段类型建议

| 逻辑类型 | 数据库类型建议 | 说明 |
|---|---|---|
| ID | `BIGINT` | 技术主键统一使用应用层雪花 ID 发号；跨表关联均使用同类型，不依赖数据库自增主键 |
| 业务编号 | `VARCHAR(32)` | 如订单号、退款单号、发票申请号、采购单号；创建后不可修改 |
| 短文本 | `VARCHAR(64)` / `VARCHAR(128)` / `VARCHAR(255)` | 编码、名称、外部流水号按长度分级设置 |
| 长文本 | `TEXT` | 备注、失败原因、说明、操作原因 |
| 枚举 | `VARCHAR(32)` | 保存稳定英文编码，不保存中文展示名 |
| 金额 | `BIGINT` | 统一按“分”保存，字段命名建议使用 `_cent` 后缀 |
| 税率/比例 | `DECIMAL(10,4)` | 税率、比例、手续费率等 |
| 数量 | `INT` | 库存、课节排序、重试次数、购买数量 |
| 布尔 | `TINYINT(1)` | 0 否，1 是 |
| 日期 | `DATE` | 到货日期、账单日期等 |
| 时间 | `DATETIME(3)` | 业务时间、创建时间、更新时间，建议精确到毫秒 |
| JSON | `JSON` | MySQL 8 可直接使用 `JSON`；若数据库不支持，使用 `TEXT` 并由应用层校验结构 |
| 文件引用 | `VARCHAR(255)` / `JSON` | 单文件用对象存储 key 或文件编号；多文件列表使用 JSON，必要时关联 `sys_file_asset` |

## 4. 通用字段、审计字段与软删除

### 4.1 通用审计字段

| 字段 | 类型建议 | 适用范围 | 说明 |
|---|---|---|---|
| `created_at` | `DATETIME(3)` | 全部业务表 | 创建时间，必填 |
| `created_by` | `BIGINT` | 除外部回调流水、日志明细外建议保留 | 创建人；系统任务可为空或记录系统用户 |
| `updated_at` | `DATETIME(3)` | 可更新业务表 | 最近更新时间，必填 |
| `updated_by` | `BIGINT` | 可更新业务表 | 最近更新人 |
| `version` | `BIGINT` | 订单、退款、发货、发票、库存、采购等并发敏感表 | 乐观锁版本号 |
| `remark` | `TEXT` | 需要业务备注的表 | 内部备注，不替代操作日志 |

### 4.2 软删除策略

| 表类型 | 策略 | 字段建议 |
|---|---|---|
| 主数据表 | 可软删除，但优先通过 `status` 停用、下架或禁用 | `deleted_flag TINYINT(1)`、`deleted_at DATETIME(3)`、`deleted_by BIGINT` |
| 交易单据表 | 不软删除、不物理删除，错误通过状态、冲正、红冲、关闭原因或操作日志表达 | 不建议设置 `deleted_flag` |
| 流水与日志表 | 不允许修改关键业务字段，不允许删除 | 不建议设置 `deleted_flag`；按归档策略迁移冷数据 |
| 多态关联表 | 不物理删除；失效关系可设置 `status` 或关闭时间 | 可选 `status VARCHAR(32)` |

主数据如课程、规格、SKU、供货商、角色已被订单或采购引用后不得物理删除。交易单据如需“取消”“关闭”“红冲”“人工作废”，应通过状态字段和操作日志记录，不应删除历史记录。

## 5. 外键与逻辑关联策略

| 关联类型 | 建议策略 | 说明 |
|---|---|---|
| 同聚合强依赖 | 可使用物理外键或强应用校验 | 如 `trade_order_item.order_id`、`fulfillment_shipment_item.shipment_id`、`purchase_order_item.purchase_id` |
| 跨模块核心单据 | 建议逻辑外键 + 必备索引 | 如支付、退款、发票、对账关联订单；避免跨模块级联删除和迁移成本 |
| 主数据引用 | 逻辑外键 + 快照 | 订单明细引用课程、规格、SKU 时，同时保存快照，避免主数据变化污染历史订单 |
| 多态关联 | `related_object_type + related_object_id + related_object_no` | 通知、审批、操作日志、代账材料关联多类业务对象 |
| 订单单据链 | 子表直接 `order_id` + `order_document_link` 索引表 | 直接关联保证查询准确，链路索引表保证订单详情页和导出效率 |

所有逻辑外键字段必须建立普通索引。任何业务表不得依赖级联删除清理历史数据。

## 6. 订单单据链核心设计

| 目标 | 设计建议 |
|---|---|
| 订单追支付 | `pay_payment.order_id`、`pay_payment.order_no` 直接关联订单；`merchant_order_no` 和 `external_payment_no` 支持对账匹配 |
| 订单追发货 | `fulfillment_shipment.order_id` 直接关联订单；发货明细、物流轨迹冗余 `order_id` 便于订单详情和售后判断 |
| 订单追退款 | `pay_refund.order_id`、`pay_refund.payment_id` 关联订单和原支付；退款明细关联订单明细 |
| 订单追发票 | `tax_invoice.order_id` 直接关联订单；红冲时记录 `source_refund_id` 或红冲原因 |
| 订单追对账 | `finance_reconciliation_record.order_id`、`payment_id`、`refund_id` 同时保留，支持收款、退款、手续费差异追溯 |
| 订单追代账材料 | `acct_material.order_id` 可直接保存订单；`acct_material_relation.order_id` 对所有关联对象做订单维度冗余 |
| 统一单据链视图 | `order_document_link` 记录订单与支付、权益、发货、退款、发票、对账、代账材料的链路索引 |

`order_document_link` 不替代子表真实关系，建议由各业务单据创建、状态变化、人工补录时同步写入或异步补偿重建。

## 7. 核心表清单

| 模块 | 表名 | 用途 | 是否软删除 | 是否直接关联订单 |
|---|---|---|---|---|
| 用户与权限 | `sys_user`、`sys_role`、`sys_user_role` | 用户、角色、授权关系 | 主数据可软删或停用 | 否 |
| 线索与学员 | `crm_lead`、`edu_student`、`student_address`、`student_invoice_title` | 线索、学员、地址、发票抬头 | 主数据可软删或停用 | 线索可关联转化订单 |
| 课程与学习 | `course`、`course_spec`、`course_lesson_node`、`learning_entitlement` | 课程、规格、课节、学习权益 | 课程主数据可软删；权益不软删 | 权益直接关联订单 |
| 交易订单 | `trade_order`、`trade_order_item`、`order_document_link` | 订单主单、明细、单据链索引 | 否 | 是 |
| 支付退款 | `pay_payment`、`pay_refund`、`pay_refund_item` | 支付记录、退款单、退款明细 | 否 | 是 |
| 履约库存 | `fulfillment_shipment`、`fulfillment_shipment_item`、`logistics_trace`、`inventory_sku`、`inventory_stock_flow` | 发货、物流、SKU、库存流水 | SKU 可软删；发货和流水不软删 | 发货和库存流水可关联订单 |
| 采购供应 | `supplier`、`supplier_sku`、`purchase_order`、`purchase_order_item`、`purchase_receipt` | 供货商、采购、收货入库 | 供货商主数据可软删；采购不软删 | 采购通常不直接关联订单 |
| 发票税务 | `tax_rule`、`tax_invoice`、`tax_invoice_item` | 税务规则、发票、发票明细 | 税务规则可软删；发票不软删 | 发票直接关联订单 |
| 对账代账 | `finance_reconciliation_batch`、`finance_reconciliation_record`、`acct_material`、`acct_material_relation` | 对账批次、对账明细、代账材料 | 否 | 对账和材料直接或间接关联订单 |
| 通知审批 | `notify_message`、`approval_record` | 通知、审批和待办结果 | 否 | 可按业务对象关联订单 |
| 配置审计 | `sys_file_asset`、`integration_callback_event`、`audit_operation_log` | 文件、外部回调、审计日志 | 否 | 可选关联订单 |

## 10. 关键唯一键与幂等键

| 场景 | 表 | 唯一键或幂等键 | 说明 |
|---|---|---|---|
| 订单创建 | `trade_order` | `order_no`、`merchant_order_no` | 订单号和支付商户订单号均全局唯一 |
| 支付回调 | `pay_payment` | `external_payment_no`、`idempotency_key` | 建议幂等键由 `merchant_order_no + external_payment_no` 组成 |
| 权益开通 | `learning_entitlement` | `student_id + order_id + course_id` | 支付成功重复回调不得重复开通 |
| 发货确认 | `fulfillment_shipment` | `shipment_no`、`tracking_no` | 防止重复发货和重复保存运单 |
| 物流轨迹 | `logistics_trace` | `tracking_no + logistics_node_time + node_status` | 重复物流回调不重复写轨迹 |
| 退款回调 | `pay_refund` | `refund_no`、`external_refund_no`、`idempotency_key` | 已退款终态不得被失败回调覆盖 |
| 发票开具 | `tax_invoice` | `invoice_apply_no`、`invoice_no`、`red_invoice_no` | 正票、红票号码均唯一 |
| 采购入库 | `purchase_receipt` | `purchase_no + inbound_batch_no` | 防止重复确认收货导致重复入库 |
| 库存流水 | `inventory_stock_flow` | `flow_no`、`idempotency_key` | 发货扣减、采购入库、调整均要可追溯 |
| 对账导入 | `finance_reconciliation_batch` | `bill_month + bill_source + file_digest` | 防止同一账单重复导入 |
| 对账明细 | `finance_reconciliation_record` | `batch_no + record_type + merchant_order_no + external_transaction_no` | 防止重复对账明细 |
| 代账材料 | `acct_material` | `material_no` | 材料申请和归档追踪 |
| 材料关联 | `acct_material_relation` | `material_id + related_object_type + related_object_id` | 同一材料不重复关联同一对象 |
| 通知发送 | `notify_message` | `idempotency_key + channel + receiver_user_id` | 同一业务事件不重复通知同一接收人 |
| 审批提交 | `approval_record` | `approval_type + related_object_type + related_object_id + status=PENDING` | 同一对象同一审批类型不允许重复待审 |
| 外部回调 | `integration_callback_event` | `source_system + event_no`、`idempotency_key` | 统一记录重复、乱序、失败回调 |

## 12. 订单关联完整性要求

| 子单据 | 必填关联 | 冗余字段 | 订单详情追溯方式 |
|---|---|---|---|
| 支付记录 | `order_id` | `order_no`、`merchant_order_no` | 通过 `pay_payment.order_id` 查支付流水，同时写 `order_document_link` |
| 学习权益 | `order_id`、`order_item_id` | `order_no`、课程快照 | 通过 `learning_entitlement.order_id` 查权益开通和退款后冻结/撤销 |
| 发货单 | `order_id` | `order_no`、收货地址快照 | 通过 `fulfillment_shipment.order_id` 查发货、物流、签收 |
| 退款单 | `order_id`、`payment_id` | `order_no` | 通过 `pay_refund.order_id` 查退款审核、原路退款、人工退款 |
| 发票单 | `order_id` | `order_no`、发票抬头快照、税务快照 | 通过 `tax_invoice.order_id` 查开票、失败、人工开票、红冲 |
| 对账记录 | `order_id`、可选 `payment_id` / `refund_id` | `order_no`、`merchant_order_no` | 通过 `finance_reconciliation_record.order_id` 查收款、退款、手续费差异 |
| 代账材料 | `order_id` 或 `acct_material_relation.order_id` | `order_no`、关联对象编号 | 通过材料主表或材料关联表按订单查询收入、退款、发票、对账材料 |
| 审计日志 | 可选 `order_id` | `target_no`、快照 | 对订单相关敏感操作直接按 `order_id` 检索 |

若子单据本身通过退款、发票或对账间接关联订单，也建议在落库时补写 `order_id`，避免订单详情、导出和审计查询依赖多级联查。

## 13. 下游实现注意事项

| 事项 | 建议 |
|---|---|
| 金额字段 | 全部按分保存，页面和接口转换为元；退款金额、发票金额、对账金额均不得使用浮点数 |
| JSON 快照 | 快照字段只追加业务必要信息，不保存密钥、完整外部回调原文和过度冗余数据 |
| 枚举维护 | 建议由应用枚举统一约束，数据库只保存编码；接口文档复用同一编码 |
| 交易删除 | 订单、支付、退款、发货、发票、对账、代账材料不做物理删除入口 |
| 外部回调 | 原始回调可保存脱敏摘要到 `integration_callback_event.raw_snapshot`，敏感字段必须脱敏 |
| 大表归档 | 审计日志、外部回调、物流轨迹、对账明细后期可按月份归档，但归档后仍需支持按订单追溯 |
| 分库分表 | 当前毕业设计和本地演示阶段不建议提前分表；后续若订单量增长，可优先按订单创建月份对流水类表做归档 |
