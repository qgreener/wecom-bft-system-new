# 16-开发任务拆分与迭代计划

## 1.总体开发策略

| 策略项 | 说明 |
|---|---|
| 以业务闭环切片 | 本系统以订单为核心串联线索、学员、课程、支付、权益、发货、退款、开票、对账和代账材料。如果按纯前端、后端、数据库切开，容易出现接口、状态机、权限和副作用长期无法闭环验证的问题；因此推荐按业务能力纵向切片，每个阶段都交付可运行、可测试、可验收的结果。 |
| 串行阶段推进 | 本项目状态机、权限、幂等、外部回调和单据链强耦合，多个大阶段并行容易导致枚举、表结构、接口和页面口径分叉。串行推进能让每一阶段先固化基础，再把已验证的领域能力交给下一阶段使用。 |
| 控制 session 上下文 | 单个开发 session 不应同时处理全部模块。建议一个 session 最多处理一个阶段；S5、S6、S7、S8 这类复杂阶段还应继续拆成阶段内小执行计划，例如“订单创建与支付回调”“退款状态机与副作用”“PC 订单详情与单据链”。 |
| 阶段计划再拆执行计划 | 本文只定义阶段顺序、输入文档、任务包、验收和交接规则。每个阶段正式开发前，应先基于本阶段输入文档生成“小执行计划”，再细化到具体代码、测试和迁移任务。 |
| 每阶段必须可验收 | 阶段结束时必须留下可启动服务、可访问页面、可调用接口、可执行测试、可复用迁移或可演示 Mock 场景之一，不能只提交半成品结构。 |
| 不继承旧系统 | 当前目录位于历史 `wecom-bft-system` 下，但历史代码、数据库、接口、架构和配置不作为新系统依据。工程、表结构、接口、状态和页面均以 `00-15` 设计文档与原型文档为准。 |
| 先闭环后扩展 | P0 主链路优先于 P1/P2 报表、自动化外部接入和预测分析。真实外部系统可延后，前提是 Mock 仍走正式适配层、正式回调、正式幂等和正式状态机。 |

## 3.阶段详细计划

#### 阶段目标

确认本次开发以新系统文档为唯一依据，不继承历史失败工程。梳理后续阶段的阅读边界、文档冲突处理规则、工程目录和阶段交接格式，避免从第一阶段就把上下文扩散到全部模块。

| `13-技术选型与总体架构设计.md` | 确认模块化单体、外部适配层、部署架构 |

| 数据库无法支撑订单单据链 | 订单详情、售后、对账、审计不可追溯 | 补齐 `order_id`、`order_no`、`order_document_link` 和索引 |
| 支付成功后置动作缺失 | 学员无法学习、发货任务缺失、线索不能转化 | 补齐支付记录、权益、通知、发货任务、线索转化、对账基础 |
| 退款成功副作用缺失 | 权益、红冲、发货、对账、代账不一致 | 补齐权益冻结/撤销、提醒停止、红冲待办、发货限制、对账影响 |
| 权限数据范围无法验证 | 存在越权访问和敏感字段泄露风险 | 补齐后端权限、数据范围、字段脱敏和导出校验 |
| 外部回调幂等无法验证 | 重复或乱序回调可能重复开通权益、扣库存、开票 | 补齐回调事件落库、业务幂等键和终态保护 |
| 核心 P0 用例失败 | 影响毕业设计和主业务演示 | 停止进入下一里程碑，优先修复 P0 |
| Mock 绕过正式链路 | 演示通过但真实接入不可复用 | 改为统一适配、统一回调、正式状态和正式表 |
| 真实密钥或敏感配置入库/入文档/入前端 | 安全风险和交付风险 | 立即移除，改为占位符和服务端环境变量 |
| 发货库存或采购入库不幂等 | 库存余额和流水不可信 | 补齐库存流水、幂等键、补偿入口 |
