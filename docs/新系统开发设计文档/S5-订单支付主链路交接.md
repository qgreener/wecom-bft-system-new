## 5. 模型说明

| 模型 | S5 使用口径 |
|---|---|
| 订单主单 `trade_order` | 保存订单号、商户订单号、学员、来源、客户端请求号、确认令牌、课程/价格/税务/地址快照、金额、支付截止时间和四类状态。 |
| 订单明细 `trade_order_item` | 保存课程、规格、数量、单价、应付、是否含实物、主 SKU、赠品 SKU、课程快照、规格快照和税务快照。 |
| 支付记录 `pay_payment` | 支付成功回调金额一致后写入；保存支付单号、订单、商户订单号、渠道、支付方式、外部流水、回调事件号、幂等键和原始摘要。 |
| 回调事件 `integration_callback_event` | 支付回调第一步落库；按 `source_system + event_no` 去重，保存事件类型、幂等键、业务对象、原始摘要、处理状态和失败原因。 |
| 发货任务 `fulfillment_shipment` / `fulfillment_shipment_item` | 含实物订单支付成功后生成 `PENDING_SHIPMENT` 任务和明细；不扣库存、不确认发货，交给 S6。 |
| 通知 `notify_message` | 支付成功后生成站内通知，按 `ORDER_PAID:{order_id}:{user_id}` 幂等。 |
| 单据链 `order_document_link` | 关联支付、权益、发货、通知、线索等子单据；S6/S7 后续子单据继续写入同一链路。 |
| 审计 `audit_operation_log` | 记录订单创建、支付拉起、取消、超时关闭、支付回调成功/失败、支付记录、发货任务、通知、后置动作失败等操作。 |

## 6. 订单确认、创建、继续支付、取消、超时关闭规则

| 场景 | 规则 |
|---|---|
| 订单确认 | 必须已登录且手机号已授权；课程必须上架、规格启用；含实物必须选择有效收货地址；返回确认快照和 `confirm_token`，不生成正式订单。 |
| 价格变化 | 创建订单时重新构建快照并校验 `confirm_token` 和 `confirmed_payable_amount_cent`；不一致则要求重新确认。 |
| 创建订单 | 必填 `Idempotency-Key`；初始化 `payment_status=PENDING`、`refund_status=NONE`、`invoice_status=NOT_APPLIED`，`fulfillment_status` 按商品属性初始化。 |
| 创建幂等 | 相同学员和幂等键重复创建返回同一订单；课程、规格、数量、地址或金额不同返回状态冲突。 |
| 继续支付 | 仅 `PENDING` 且未超时订单可拉起支付；返回 Mock 参数、商户订单号、支付截止时间、正式回调路径和 Mock 触发路径。 |
| 取消订单 | 仅待支付订单可取消；已关闭重复取消返回当前状态；已支付订单不可取消。 |
| 超时关闭 | 拉起支付时若订单已过支付截止时间，自动置为 `CLOSED`，写关闭原因 `PAYMENT_TIMEOUT` 和审计。 |

## 7. 支付回调先落库和幂等处理

| 项 | 说明 |
|---|---|
| 正式入口 | `POST /api/callbacks/payments/wechat`。 |
| Mock 入口 | `POST /api/app/orders/{order_id}/mock-pay` 只构造正式回调命令并复用正式处理链路，不直接改订单。 |
| 落库顺序 | 先调用 `CallbackEventRepository.recordReceived` 写 `integration_callback_event`，再执行业务处理。 |
| 事件幂等 | `source_system + event_no` 重复时直接返回既有处理结果。 |
| 支付业务幂等 | `merchant_order_no + external_payment_no` 作为支付业务幂等键，防止重复写 `pay_payment`。 |
| 金额不一致 | 回调金额与订单应付不一致时，回调事件标记 `FAILED`，订单保持 `PENDING`，不写支付记录，不执行后置动作。 |
| 状态冲突 | 已关闭或非待支付订单收到成功回调时，回调事件进入失败待核对口径，不把订单置为已支付。 |

## 8. 支付成功后置动作

| 后置动作 | 幂等口径 |
|---|---|
| 学习权益 | 调用 S4 `LearningEntitlementService.openForPaidOrder`，按 `student_id + order_id + course_id` 幂等。 |
| 发货任务 | 含实物订单查重后创建 `fulfillment_shipment` 和 `fulfillment_shipment_item`，状态为 `PENDING_SHIPMENT`。 |
| 站内通知 | 按 `ORDER_PAID:{order_id}:{user_id}` 查重，只生成一条支付成功站内通知。 |
| 线索转化 | 调用 S4 `LeadApplicationService.convertPaidLead`，优先企微外部联系人，其次手机号匹配；匹配不到不影响订单和权益。 |
| 单据链 | 支付、权益、发货、通知、线索均通过 `order_document_link.upsert` 写链路，重复回调不重复生成链路记录。 |
| 副作用失败 | 支付主状态和支付记录不回滚；回调事件标记失败原因，并写 `PAYMENT_SUCCESS_SIDE_EFFECT_FAILED` 审计。 |

## 11. Mock 支付场景与正式回调复用

| 场景 | 验收口径 |
|---|---|
| 正常支付成功 | 小程序 Mock 入口投递正式回调命令；金额一致后订单置为 `PAID`，支付记录存在，后置动作执行。 |
| 重复成功回调 | 重复同一事件或同一支付流水不重复生成支付记录、权益、发货任务、通知、线索转化和单据链。 |
| 金额不一致 | 正式回调入口返回 `202`，事件状态 `FAILED`，订单保持 `PENDING`。 |
| 已关闭后回调 | 进入异常待核对口径，不自动改为已支付。 |
| 真实接入边界 | S5 不接真实微信支付；S11 接入真实/沙箱时应复用 `/api/callbacks/payments/wechat`、回调事件落库、业务幂等和异常待处理口径。 |

本阶段必须覆盖：
- S6-T1：SKU 与库存基础。SKU、安全库存、库存流水、手动入库/出库基础；库存余额变更必须有流水。

- S6-T3：物流轨迹与签收。物流回调写轨迹，重复/乱序轨迹不回退主状态；签收同步发货单和订单履约状态。

- S6-T5：采购与供货商协同。采购单、采购明细、大额审批、供货商确认/拒绝/填写物流基础能力。
- S6-T6：采购入库与单据链。采购收货入库生成库存流水，采购、发货、库存、物流、订单单据链可追溯。
