# 新系统开发设计文档说明

## 1.文档定位

本目录为新系统开发设计文档，用于承接《原型设计方案》并支持后续模块设计、数据库设计、接口设计、测试验收和毕设演示。

需要特别说明：当前目录虽然位于 `D:\java-code\wecom-BFT-system\docs` 下，但 `wecom-bft-system` 是历史失败产物，仅作为当前文档的目录承载位置。历史代码、历史数据库、历史接口、历史架构和历史配置不作为本次新系统的设计依据，除非后续文档明确标注“参考”或“复用”。

## 2.需求来源

本目录后续文档只以下列原型文档作为主要需求来源：

| 序号 | 文档 | 用途 |
|---|---|---|
| 1 | `docs/原型设计方案/README.md` | 系统概要、范围说明、三端文档入口 |
| 2 | `docs/原型设计方案/PC管理端.md` | PC 管理端页面、角色操作、后台业务能力 |
| 3 | `docs/原型设计方案/小程序端.md` | 学员端课程、下单、学习、退款、发票、地址流程 |
| 4 | `docs/原型设计方案/企微外部协同端.md` | 企微侧边栏、供货商 H5、审批消息、企微通知卡片、公开留资页 |
| 5 | `docs/原型设计方案/交互与联调说明.md` | 支付、退款、物流、开票、红冲、对账等联调口径 |
| 6 | `docs/原型设计方案/系统设计约束.md` | 端侧边界、权限边界、单据链、状态口径、财税口径、外部接口约束 |

## 3.设计边界

| 项目 | 处理原则 |
|---|---|
| 历史代码 | 不默认读取、不默认继承、不作为模块划分依据 |
| 历史数据库 | 不默认沿用表结构、字段、枚举和索引 |
| 历史接口 | 不默认沿用路径、参数、响应结构和鉴权方式 |
| 历史前端页面 | 不默认复用路由、组件、状态管理和样式 |
| 当前原型文档 | 作为新系统需求源和页面交互参考；本次确认后原型文档冻结，字段、状态、接口和部署口径以新系统开发设计文档为准 |
| 可复用内容 | 只有在文档中明确标注“参考”或“复用”时才纳入 |

## 6.冲突处理规则

当后续文档之间或后续文档与原型文档之间出现口径不一致时，按以下优先级处理：

| 优先级 | 文档或规则 | 说明 |
|---|---|---|
| 1 | `系统设计约束.md` | 优先处理端侧边界、状态拆分、单据链、财税口径和外部接口边界 |
| 2 | `交互与联调说明.md` | 优先处理支付、退款、物流、开票、红冲、对账等联调结果 |
| 3 | 当前目录中编号更靠前的设计文档 | 例如 `03-模块设计文档.md` 应约束后续数据库和接口设计 |
| 4 | 三端页面原型文档 | 用于确认页面展示、操作入口和用户交互 |
| 5 | README 概要 | 用于确认整体范围，不替代详细设计 |

如果冲突无法通过上述规则判断，后续文档应显式标注“待确认”，并在修订时回写到相关上游文档，避免多个文档长期保留不同口径。

原型设计方案后续不再持续同步维护。若原型页面描述与本目录设计文档冲突，应优先修订本目录设计文档或在本目录补充映射说明，不再要求两套文档长期完全一致。

## 7.核心约束提醒

| 约束 | 说明 |
|---|---|
| 新系统约束 | 本系统按当前原型重新设计，不默认继承历史失败产物 |
| 订单中心约束 | 系统以订单为中心串联支付记录、学习权益、发货单、退款单、发票单、对账记录和代账材料 |
| 状态拆分约束 | 订单必须拆分为支付状态、履约状态、退款状态和开票状态，不使用单一订单状态混合表达全流程 |
| 退款闭环约束 | 退款成功后必须处理学习权益、提醒、发票红冲、实物退货判断和对账影响 |
| 外部接口约束 | 企微、微信支付、物流、电子发票等外部能力必须保留失败、异常待处理和人工补偿入口 |
| 财税口径约束 | 税负率、财税预测和经营建议仅作经营参考，不作正式税务申报依据 |

## 8.Mock 与真实接入边界

Mock 仅作为外部系统的替身实现，用于本地开发、联调演示、异常流程验证和毕设答辩演示。Mock 不应改变业务模型、状态机、接口契约和验收口径；从 Mock 切换到真实平台接入时，应以替换适配实现和调整环境配置为主，不应重写核心业务流程。

| 边界项 | 规则 | 后续落点 |
|---|---|---|
| 统一契约 | 支付、退款、物流、电子发票、企微通知等外部能力必须先定义系统内部统一接口契约，Mock 实现和真实实现共用同一入参、出参、状态枚举、错误码和幂等规则 | `03-模块设计文档.md`、`06-API接口文档.md` |
| 适配层隔离 | 业务层只依赖统一适配接口，不直接依赖 Mock 类、真实平台 SDK 或平台特有字段 | `03-模块设计文档.md` |
| 配置切换 | Mock、沙箱、真实接入应通过环境配置或系统配置切换，不通过修改业务代码切换 | `07-外部系统联调文档.md`、`10-服务器部署与演示说明.md` |
| 回调同链路 | Mock 支付成功、退款成功、物流更新、开票完成等事件必须模拟外部回调进入系统，走真实回调处理、幂等校验和状态机流转 | `02-业务流程与状态机说明.md`、`06-API接口文档.md`、`07-外部系统联调文档.md` |
| 回调路径统一 | Mock、沙箱、真实接入共用 `/api/callbacks/**` 回调路径，通过适配层、签名校验和环境模式区分来源，不新增 Mock 专用业务回调路径 | `06-API接口文档.md`、`07-外部系统联调文档.md` |
| 状态不分叉 | Mock 不得增加仅演示环境存在的订单、退款、物流、开票状态；页面、接口、测试均使用正式状态枚举 | `02-业务流程与状态机说明.md`、`04-领域模型与数据字典.md` |
| 数据不污染 | Mock 不使用临时表、特殊字段或演示专用状态污染正式领域模型；必要的模拟流水应按正式支付记录、退款单、物流单、发票单结构落库 | `04-领域模型与数据字典.md`、`05-数据库设计文档.md` |
| 不绕过业务 | Mock 不得直接修改订单、退款、发货、发票等核心状态，必须通过业务服务或回调处理链路触发状态变化 | `02-业务流程与状态机说明.md`、`03-模块设计文档.md` |
| 异常一致 | Mock 不只模拟成功，也要支持失败、超时、重复回调、回调乱序、人工处理、异常待处理等场景 | `07-外部系统联调文档.md`、`09-测试与验收用例.md` |
| 验收复用 | 同一套核心验收用例应能在 Mock 环境和真实沙箱环境复用，差异仅来自外部配置、凭证和平台返回数据 | `09-测试与验收用例.md`、`10-服务器部署与演示说明.md` |

后续文档如涉及外部能力，必须明确区分“系统内部统一契约”“Mock 实现口径”“真实平台接入口径”和“异常补偿口径”。不得把 Mock 的便捷处理写成正式业务规则，也不得为了演示效果绕过订单状态、退款状态、履约状态、开票状态和单据链约束。

## 9.后续编写要求

1. 所有文档使用中文编写。
2. Markdown 文件统一使用 UTF-8 编码。
3. 优先使用表格整理模块、字段、状态、接口、权限和测试用例。
4. 不在开发设计文档中直接写具体密钥、真实接口地址和敏感配置。
5. 不在未确认的情况下引用历史代码作为事实依据。
6. 每个文档应能被单独阅读，但涉及状态、字段和接口时必须与上游文档保持一致。
